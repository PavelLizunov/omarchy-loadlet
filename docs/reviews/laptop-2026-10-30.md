## Findings: verified mechanisms and proposed minimal remedies

Severity describes local impact and preconditions, not an official Marketplace rating. "Reproduced" below identifies the test boundary; mocked-service evidence is not a physical systemd or hardware experiment.

### F01 — High: quadratic GPU ingestion blocks the shared UI thread

**Anchors:** `Model.js:454-462`, `Model.js:563-579`; caller `ActivityController.qml:340-348`.

`parseGpuSnapshot()` searches the growing `processGpus` array with `filter()` for every engine row. `nextProcessGpus()` scans the entire previous array for each current item. Both run synchronously in QML JavaScript. A legal 67842-byte snapshot with 1000 process-engine identities is well below the 256 KiB transport cap.

In an inert actual-consumer Qt 6.12 fixture, 10 iterations per size measured:

| Identities | Frame bytes | Parse mean ms | Delta mean ms |
| --- | ---: | ---: | ---: |
| 100 | 6632 | 1.3 | 1.7 |
| 500 | 33832 | 15.4 | 35.1 |
| 1000 | 67842 | 400.3 | 796.5 |

This is a synthetic stress case, not the current desktop's GPU process count. It demonstrates a reachable input-size/UI-stall mechanism, not a measured normal-session freeze. Use temporary maps keyed by PID/start ticks/GPU, preserving existing aggregation semantics, instead of repeated full-array scans.

### F02 — High: ignored GPU stop failure can commit a false successful profile

**Anchors:** `power-profile:241-247`, restoration consumer `power-profile:502-506`.

Old GPU services are disabled/stopped with `check=False`. The new `active.json` is then committed and new services enabled. A failed stop can leave the old worker alive with its cached percentage; removing a GPU from the profile can also discard the identity needed for later recovery. A temporary-state/mocked-service reproduction returned success and removed the GPU from active state even when stop returned failure. Require confirmed termination before replacing state; take a recoverable failure path otherwise.

### F03 — High: one rollback error skips all remaining restoration

**Anchors:** `power-profile:248-260`, related sequence `power-profile:369-383`.

`restore_cpu(previous)` is the first unprotected operation inside exception recovery. If it raises, subsequent motherboard/GPU cleanup and persistence restoration never run. A mocked GPU stop timeout followed by an injected CPU rollback write failure produced exactly one systemd call and no later recovery attempt. Attempt independent recovery steps even after another fails, retain unresolved state, and report incomplete restoration.

### F04 — Medium: Fan Restore is not serialized with Save/temporary overrides

**Anchors:** lock owner `fan-control:68-81`, callers `fan-control:312-319`, `fan-control:326-333`, `fan-control:343-353`.

Restore omits the existing per-channel switching lock. Save can finish between Restore's profile deletion and service disable, leaving a saved new profile with its worker stopped. A deterministic simulated interleaving left 70% saved after Restore completed. This proves the mutation sequence admits the race; no real concurrent hardware/service experiment was performed. Wrap the complete Restore transaction in the same per-channel lock.

### F05 — Medium: a failed standalone fan Save persists the rejected target

**Anchors:** `fan-control:312-319`; service retry policy `fan-control:90-97`.

The saved percentage is replaced before service activation succeeds, without local rollback. With temporary files and failed mocked startup, an old 80% choice became 20% despite request failure. A later retry/reboot may activate the failed target; actual restart behavior was not exercised. Restore previous saved/enabled intent when activation fails, including first-save cleanup.

### F06 — Medium: manual fan control can fail to cancel persistent automation

**Anchors:** `fan-control:240-243`; persistent owner `power-profile:363`; runtime directory `power-profile:400-403`.

The request wrapper calls `auto-off` only if the transient runtime status file exists. During startup/restart that file can be absent while persistent auto configuration remains. The isolated wrapper probe confirmed that absent status permits a manual command without attempting `auto-off`. Invoke the installed adapter's idempotent cancellation from the manual request path rather than using transient status existence as authority. Keep internal profile fan operations separate to avoid recursive cancellation.

### F07 — Medium: sensor recording can stop flushing permanently under buffer pressure

**Anchors:** `DiagnosticJournal.h:149-161`; native caller `activity-sampler.cpp:2210-2213`.

A new record that would exceed 128 KiB returns before the overdue flush. Four legal approximately 28 KiB records can occupy about 112 KiB before the fifth arrives at the 60-second flush boundary. Subsequent records continue failing without draining the buffer. A friend-fixture injecting that reachable buffered state reproduced repeated `sensor_record_capacity` even with a flush overdue by 120 seconds. No production history was written. Flush under pressure before rejecting an otherwise legal record. This laptop's 592-byte sensor frame does not reach the condition.

### F08 — Medium: diagnostic context is discarded for many CPU policy rows

**Anchors:** `DiagnosticJournal.h:47-62`, `DiagnosticJournal.h:163-168`.

Collection admits up to 64 CPU policies, but `Context()` replaces the entire payload with `null` above 10000 bytes. A generated 32-policy amd-pstate fixture produced **15832 bytes**, then `context_capacity` and `null`, losing PSI and CPU policy evidence along with the policy list. Budget/truncate policy details explicitly while retaining other context; do not merely raise the limit beyond the complete journal record budget.

### F09 — Medium: one missing sensor deletes its volatile history

**Anchors:** `Model.js:115-128`; assignment `ActivityController.qml:325`.

The next-history object contains only sensors present in the current snapshot. A transient read failure or sleeping GPU removes the complete prior series; reappearance starts fresh. Direct execution of the actual Model produced a retained GPU point at sample 10 and no GPU key after a CPU-only sample 13. Retain missing series within an explicit finite age/key budget and mark gaps when observations resume; blindly keeping every historical key would introduce a new unbounded-growth path. Persisted history is a separate source and is not deleted by this particular defect.

### F10 — Medium: backward wall-clock changes pause sensor recording

**Anchors:** `DiagnosticJournal.h:151-153`.

The 15-second gate uses `time_t`, not steady time. A backward adjustment makes the delta negative and suppresses records until the clock catches up. Injecting a previous timestamp one hour ahead skipped a valid record without changing the real system clock. Use monotonic time for admission and wall time only for record timestamps.

### F11 — Medium: failed status reads retain a successful automation state

**Anchors:** `PowerProfiles.qml:159-170`, `PowerProfiles.qml:195`, labels/toggle at `PowerProfiles.qml:25-26,201-203,250-255`.

Malformed output, exit failure or timeout does not invalidate cached capabilities/automation. An inert actual-consumer probe delivered a valid gaming status and then malformed output plus exit 1; `capabilitiesReady` and `automatic.gaming` both stayed true. Expire received state locally and represent unavailable status explicitly. Helper-side freshness cannot protect a UI that receives no subsequent valid response.

### F12 — Medium, hardware-dependent consequence: CPU thermal discovery reads suspended non-CPU sensors

**Anchors:** `activity-sampler.cpp:1004-1008`, `activity-sampler.cpp:1159-1195`.

The CPU-temperature discovery path reads every `temp*_input` before ranking chip/label and lacks the power-state guard used by full sensor/GPU collection. With synthetic sysfs and inotify, two `thermals` requests accessed an `amdgpu` temperature whose runtime status was `suspended`. When no CPU sensor is accepted, discovery repeats on every request. Filter candidates before dynamic reads, honor runtime state, and back off failed discovery. Actual GPU resume and energy impact were **not measured** and depend on driver behavior.

### F13 — Medium, conditional producer support: mixed GPU record types split one identity

**Anchors:** `Model.js:449-461`, `Model.js:563-579`; producer combines NVML and DRM at `activity-sampler.cpp:1761-1772`.

`process-gpu` entries omit the `processId` field searched by `process-engine`. Supplying both for the same PID/start/GPU yields two objects. If direct utilization is unavailable, the first old object has no engines and the delta can remain unavailable. An actual-Model fixture reproduced two records and empty computed usage. Set/use one shared identity key for both formats. This laptop did not produce that combination; physical driver support remains a precondition, not an observed deployment failure.

### F14 — Low/Medium: fan drafts mask later restored/applied values

**Anchors:** `Panel.qml:101`, `Panel.qml:120-133`, `Panel.qml:1989-1992`.

Once edited, `fanOutputDrafts[channel]` takes precedence over saved/live output and is not cleared by successful Restore. An inert helper-exit probe retained draft `85` after Restore. Clear relevant drafts after accepted Save/Restore/profile changes, while preserving intentional unsaved edits on failure.

### F15 — Low: the UI wrapper's 30-second timeout is too tight here

**Anchor:** `test/ui-checks.py:179-180`.

Stock `make check` timed out in the UI runner at 30 seconds. Running the same inert suite with a 120-second outer budget passed all **86** cases; process wall time was **30.35 seconds**, Qt's reported test duration 29.29 seconds. No warning/error diagnostics occurred in that extended run. This is a wrapper budget/host-overhead issue, not evidence of an infinite loop. Give startup/import overhead margin or split independent cases; retain a finite timeout.

### F16 — Low: the unlock description understates the grant

**Anchors:** `docs/guide.md:352-357`, `fan-control:268-276`, `fan-control:289`.

The guide says "passwordless fan requests only", but the generated 24-hour fixed-helper grant also permits validated CPU/profile `apply`, `restore`, `auto-config`, and `auto-off`. This is not arbitrary sudo or demonstrated escalation. Document/message the actual CPU/fan/profile scope consistently. No host sudoers grant was installed or changed.

## Additional performance opportunities and unresolved hypotheses

- **P01, measured synthetic duplicate-FD overhead:** `activity-sampler.cpp:1994-2031,2100-2145` scans accessible process FDs without a total descriptor budget and reads PID stat inside the FD loop before deduplication. One synthetic DRM client with 64/512/4096 duplicate FDs emitted the same 231-byte result and one process-engine row, but warm median request time grew **1.17/5.86/47.80 ms**. Cache start ticks per PID per request, deduplicate earlier where identity permits, and impose explicit traversal/cache budgets without silently reporting a partial complete inventory. This is stress evidence, not a normal desktop regression.
- **P02, source-only:** `activity-sampler.cpp:1672-1699` reparses `pci.ids` during rediscovery; repeated names can be cached with a bounded identity cache. The cost at its 30-second rediscovery cadence was not isolated, and the function stops on a match rather than necessarily reading the entire file.
- **P03, measured current scan but optimization unproven:** `GameDetection.py:32-59` reads bounded environment and command-line data for every accessible same-user process before executable candidate rejection. Median full scan here was 32.91 ms. A semantics-preserving early executable filter may avoid unnecessary reads; no percentage saving is claimed. The enclosing worker catches `ValueError`, so its enumeration-cap exception is not an established service crash.
- **P04, source-only:** optional per-channel motherboard workers independently rescan CPU thermal data roughly every second; GPU fan workers poll roughly every two seconds. Neither worker CPU cost nor physical effects were measured because helpers/hardware controls were absent and not activated.
- **U01:** synchronous storage `statvfs` against a stalled local/FUSE mount can hold the single reader until watchdog recovery. No deliberately hung mount was created; this remains a supported blocking-I/O hypothesis with a watchdog counterguard, not an observed permanent system hang.
- **U02:** `Panel.qml:1683` window teardown dereference and unparented `Screen.devicePixelRatio` behavior in `SvgIcon.qml:49-50`/`ComputerMap.qml:44-45` need exact host lifecycle evidence. No native crash is claimed from possible JavaScript exceptions.
- **U03:** `activity-report:360-368` has an uncaught sensor-output-budget error path. The producer/output budgets and UI error state limit harm. A reachable supported-history fixture exceeding the final output cap was not demonstrated, so this was not promoted to a confirmed functional defect.
- **Documentation drift:** `docs/guide.md:575-578` still describes GPU work as expanded-only; `Panel.qml:898` also enables it for the compact process table. A later guide section already explains compact GPU attribution. Consolidate the explanation rather than treating the intentional work as an unrequested polling defect.

## Rejected or narrowed reviewer claims

1. **Missing `switchPanel`/Tab crash — rejected.** The installed owning `Ui/Panel.qml:33-36` provides `switchPanel(direction)`. It is inherited; the leaf inspected the wrong host location. An ordinary JS exception would not by itself prove a native crash anyway.
2. **Missing PowerProfiles/ProfileCodec/GameDetection in distribution — rejected.** They were intentionally absent from one scoped leaf bundle but exist in the actual reviewed checkout/package; install/package checks passed. A review-input omission is not a product dependency defect.
3. **Freshness clock repeatedly remaps/sorts unchanged process data — rejected for the claimed mechanism.** An actual QML fixture advanced five fresh timestamps while the boolean stayed true and observed **zero** `processesChanged` emissions. Qt propagates changed property values, not every reevaluation. Real GPU/process updates still require normal mapping/sorting.
4. **Dropdown dismissal loses focus — rejected in the tested host.** The actual inert Qt consumer restored focus to `iconShapeDropdown` after closure without the proposed manual workaround. Physical Wayland focus remains outside this evidence.
5. **4000 history points cause `Math.min.apply` stack overflow — not established.** Inputs are bounded, and the suggested 65536-element reproduction exceeded the cited production bounds. No failing supported-size Qt case was supplied.
6. **32768-process budget exception crashes game automation — rejected as stated.** `power-profile:auto_worker()` catches `ValueError` and publishes an error; absence/unavailability and cost at extreme process counts remain separate questions.
7. **Performance percentages/energy savings from source syntax — not accepted.** Static cadence and bounds do not measure energy, actual wake rate, or improvement.

Raw leaf reports contained inaccurate line counts/anchors and overly broad coverage assertions. Accepted anchors were reopened against the frozen current source; examples above were reproduced or explicitly narrowed.
